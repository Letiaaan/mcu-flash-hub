## 虚拟环境实际证明了什么

普通「虚拟演练」使用独立子进程和内存 Flash 模型，确实复制数据并计算读回哈希，故障场景会改变数据或返回错误。它验证应用如何组织任务和处理结果，不执行厂商协议。

ESP32 另有独立 TCP 虚拟 ROM，真实 esptool 通过 pyserial 的 `socket://127.0.0.1` 与之通信。服务实现有限的 ESP32 ROM 协议，包括寄存器、SLIP、块数据及 MD5，不修改 esptool。测试明确使用 `--no-stub --before no-reset --after no-reset`，因此**未覆盖实际默认流程的 RAM stub 上传、USB、复位时序和波特率电气行为**。它不是运行 ESP32 指令集的 QEMU，也不能运行用户固件。此协议测试仅针对经典 ESP32，不能据此推定 C3 / S3 的协议已经验收。

## 仍需实物验证的内容

- 每个芯片的下载模式、供电、串口电平、驱动、接线、实际容量、擦写、掉电恢复和固件启动。
- STM32CubeProgrammer 与 AVRDUDE 的真实 CLI 联调及驱动安装。本次未安装这两个外部工具，只验证了参数生成和虚拟任务。
- 精确型号匹配：STM32 和 STC 后端会自行识别设备，当前没有用所选预设强制阻止其他同系列料号；需人工核对日志。
- STC 的独立读回校验，目前不提供。USBasp 的时钟与目标供电适配、Arduino 串口 Bootloader，以及其他 STC 系列也不在范围内。
- 各工具版本差异，端口拔插、特殊安全模式、Bootloader / 分区保留区和完整生产工艺。

所有任务报告的 `hardware_acceptance` 均为 `false`。真实工具的零退出码记作「真实工具执行完成」，不会被标成「实物验收通过」。正式兼容清单应由真实芯片和烧录器的测试记录逐项建立。
